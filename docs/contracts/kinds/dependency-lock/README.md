# DependencyLock

Status: **Frozen**

`DependencyLock` records the exact external artifacts resolved for one
project. It covers both RWE libraries and installed node bundles. It does not
record project source files, secrets, generated caches, or native nodes shipped
inside the running Zebflow binary.

The Rust schema, dependency service, RWE resolver, node registry, Hub installer,
Project Studio, fixtures, and transfer tests implement this contract.

## Identity

| Item | Value |
| --- | --- |
| API version | `zebflow.com/v1` |
| Kind | `DependencyLock` |
| Canonical file | `repo/zeb.lock` |
| Representation | Strict UTF-8 JSON |
| Owner | The project named by the owning path |
| Rust definition | `src/contracts/kinds/dependency_lock.rs` |
| Read and write service | Shared dependency-lock service |
| Primary resolvers | RWE library service and node registry |

The file is generated by Zebflow. Users may review it in Git, but normal
settings and installation flows must update it through the dependency service.

JSON is intentional. Lock files need deterministic ordering, strict parsing,
stable hashing, and safe atomic replacement more than hand-editing convenience.

## Requested State And Resolved State

Requested state and resolved state have different owners.

- `zebflow.yaml` records requested RWE libraries.
- Installed node definitions and node-bundle manifests state which project node
  capabilities are requested.
- Pipeline graphs state which node kinds they use.
- RWE source states which libraries and local modules it imports.
- `zeb.lock` records the exact external artifacts that resolved those
  requirements.

A lock entry never creates a requirement by itself. Removing the final source
reference allows the dependency service to remove the unused lock entry.

## Canonical Shape

```json
{
  "apiVersion": "zebflow.com/v1",
  "kind": "DependencyLock",
  "metadata": {
    "name": "project-development"
  },
  "spec": {
    "rwe": {
      "libraries": {
        "zeb/deckgl": {
          "version": "0.1",
          "source": "hub.local",
          "source_id": "zebflow.deckgl@0.1.1",
          "entry": "rwe-libraries/zebflow.deckgl/0.1/runtime/deckgl.patched.mjs",
          "integrity": "sha256:9c1e385bc9918e55ca7214dd995efbfc73bff14806ba13ee5c3f6ffcb4761eae"
        }
      }
    },
    "nodes": {
      "bundles": {
        "zebflow.sim-des": {
          "version": "1.0.0",
          "source": "hub.public",
          "source_id": "zebflow.sim-des@1.0.0",
          "entry": "nodes/zebflow.sim-des/definition.json",
          "integrity": "sha256:3ac2f46cf9e862d73b115e2806c86d1794fa2ca6c3025dcfea1f337a48d72ef3",
          "definitions": [
            "n.x.sim.des"
          ]
        }
      }
    }
  }
}
```

The top-level namespaces are permanent:

- `spec.rwe` owns browser runtime dependencies.
- `spec.nodes` owns installed non-native node dependencies.

A future dependency family must receive its own strict namespace. It must not
place unrelated entries inside `rwe.libraries` or `nodes.bundles`.

## Metadata Rules

`metadata.name` must be the canonical project slug and must match the project
slug in the owning path.

`metadata.version`, `metadata.digest`, and `metadata.annotations` are
forbidden. The lock is mutable project state, not an independently released
package.

## Common Artifact Fields

Every RWE library and node bundle entry requires:

| Field | Meaning |
| --- | --- |
| `version` | Exact resolved artifact release |
| `source` | Provenance: `hub.local`, `hub.public`, `hub.static`, `direct.npm`, `direct.file`, or `project` |
| `source_id` | Stable source coordinate with no credential or mutable query value |
| `entry` | Normalized installed artifact path |
| `integrity` | SHA-256 digest of the resolved artifact bytes |

Names, versions, and source identifiers must be non-empty and bounded. Entry
paths must be relative, use forward slashes, and contain no empty, current, or
parent segments.

The integrity value must be `sha256:` followed by exactly 64 lowercase
hexadecimal characters. Empty, guessed, deferred, or placeholder integrity
values are forbidden.

Unknown fields are rejected at every envelope, namespace, collection, and entry
level.

## RWE Library Rules

`spec.rwe.libraries` is keyed by a lowercase namespaced library name such as
`zeb/deckgl`. In `zebflow.com/v1` an RWE source is `hub.local`, `hub.public`,
`hub.static`, `direct.npm`, or `direct.file` (restructured 2026-08-27,
pre-release, replacing `embedded`/`hub`/`file`). All five resolve identically:
against the installed copy at `data/hub/rwe-libraries/{package}/`, with `entry`
resolving against `data/hub/` the same way node-bundle entries do and
`integrity` hashing the installed bytes. `source` records **provenance, not a
resolution order** — the digest pins identity, so the resolver may satisfy an
entry from any source whose bytes match, and the dependency report may hint
(never auto-install) when a declared dependency is present in the local hub.
The lock records the serving kind and coordinate, never a host: a re-fetch may
use any configured repository offering the coordinate, provided the bytes
match the digest.

`source_id` per value: `hub.*` — the package coordinate
(`publisher.package@version`); `direct.npm` — the converted npm coordinate
(`npm/{name}@{version}`), which is what makes it weakly reproducible;
`direct.file` — the supplied package's declared identity. `hub.*` names the
serving the bytes arrived through — `hub.local` is the blessed shelf,
release-seeded and release-guaranteed content only (`distribution.md` §1b),
never user-published; `direct.*` is a `rwe_library` package that
never touched a hub (npm-converted or user-supplied), reviewed by the same
install gates. The replaced words are simply invalid: a lock carrying
`embedded` or bare `hub` is refused like any other unknown value, and ordinary
resolution regenerates the lock from requested state. There is no migration
path — nothing shipped, pre-release instances regenerate or rot. `project` RWE
ingestion is not an accepted state until a later
contract version defines and implements its resolver behavior.

An RWE library is locked when project configuration or compiled RWE imports
require it. Project-local `.ts` and `.tsx` files are source and are not lock
entries. Imports through `@/` are checked as local-file requirements.

Direct npm, JSR, and CDN package ingestion is not part of this contract. The
reviewed artifact it must produce is defined: a `rwe_library` `HubPackage`
carrying a valid `RweLibraryManifest`, entering through the local-file channel
and locking as `direct.npm` or `direct.file`. The conversion tooling itself
stays outside this contract.

## Node Bundle Rules

`spec.nodes.bundles` is keyed by the canonical lowercase bundle identity — the
package coordinate `publisher.package`, e.g. `zebflow.sim-des` — not by one
node kind. One bundle may provide several node definitions.

Each node bundle adds:

| Field | Meaning |
| --- | --- |
| `definitions` | Sorted, unique node kinds provided by the resolved bundle |

Every definition must use a valid node kind such as `n.x.telegram.send` or
`n.x.sim.des`. The lock does not police the node namespace; that rule belongs to
`NodeBundle`. A node kind cannot be provided by two locked bundles in the
same project.

Native nodes compiled into Zebflow are runtime capabilities and are not lock
entries. A pipeline using a native node is checked against the active runtime
node registry.

In `zebflow.com/v1`, node-bundle sources are `hub.*`, `direct.file`, or
`project` — a node bundle supplied as a local file installs into
`data/hub/nodes/` and locks `direct.file`. An `embedded` node bundle is a
runtime capability and must not be written to the project lock.

Composite and WASM nodes copied into project source are discovered through
their strict `NodeBundle` manifest. Each entry is normalized into a validated
`NodeDefinition`. External or binary artifacts are locked when reproducible
resolution requires them.

A Hub script or template added as editable project source is not kept as an
installed dependency. It becomes normal project source.

## Automatic Requirement Discovery

Zebflow builds a dependency requirement set from:

1. Pipeline node kinds.
2. Nested composite-node pipelines.
3. WASM and composite node definitions in installed bundles.
4. RWE libraries requested by project configuration and detected by RWE compile.
5. Project-local imports validated by the RWE compiler.
6. Installed node-bundle manifests.

The scanner and resolver are separate:

- The scanner states what the project requires.
- The resolver states what currently provides each requirement.
- The lock stores exact resolved external artifacts.
- The report explains anything unresolved.

The scanner must recurse through composite nodes and must detect cycles. The
same requirement discovered from several files is resolved once.

## Derived Dependency Report

Missing dependencies do not belong in `zeb.lock`. Zebflow derives a report
from project requirements, the lock, local files, installed definitions, and
the active runtime registry.

Each requirement has one status:

| Status | Meaning |
| --- | --- |
| `resolved` | The expected provider exists and passes validation |
| `missing` | No provider exists |
| `version_mismatch` | A provider exists at the wrong locked version |
| `integrity_mismatch` | Artifact bytes do not match the lock |
| `unsupported_runtime` | The active Zebflow runtime lacks a required native capability |

The report is API and UI output. It is not another persisted contract Kind.

Project Studio should group findings by RWE libraries, node bundles, native
runtime capabilities, and local files. A resolvable item may offer an explicit
`Add` or `Resolve` action. Zebflow must not download or install code merely
because a project was opened.

## Validation Times

Full dependency validation runs when Zebflow:

1. opens or imports a project
2. adds a Hub package or node bundle
3. compiles an RWE entry
4. registers or activates a pipeline
5. publishes a project package
6. materializes a project on another runtime

A missing dependency must not prevent the project from opening in an editable
state. It must block the affected compile, activation, publication, or
execution plan with a precise error.

A normal pipeline hit uses the validated in-memory execution plan. It does not
rescan source or parse `zeb.lock` on every request.

## Limits And Ordering

The canonical writer sorts all object keys lexically. Arrays declared as sets,
including `definitions`, are sorted and deduplicated.

Initial v1 limits:

| Item | Limit |
| --- | ---: |
| Complete lock document | 4 MiB |
| RWE libraries | 1,024 |
| Node bundles | 1,024 |
| Definitions per node bundle | 256 |
| Logical name or source ID | 256 bytes |
| Version | 128 bytes |
| Entry path | 2,048 bytes |

Cross-entry validation must reject duplicate provided node kinds and conflicting
artifact identities.

## Security Rules

The lock must not contain:

- credentials, tokens, passwords, cookies, or private keys
- signed URLs or mutable access query strings
- runtime cache paths or temporary paths
- unverified remote artifacts
- executable installation instructions
- package lifecycle scripts

A Hub or remote resolver performs policy review before writing files or lock
entries. The lock records the resulting immutable identity and digest, not the
credential used to retrieve it.

Integrity validation happens before an artifact becomes available to RWE or the
node registry.

## Writes And Concurrency

Each project has one dependency mutation lock shared by RWE and node operations.
Read, modify, validate, and write run while that lock is held.

The writer:

1. validates the complete contract
2. writes a temporary file in the same directory
3. syncs the temporary file
4. atomically replaces `zeb.lock`
5. syncs the parent directory on Unix

An operation that changes project configuration, installed node files, and the
lock must stage all changes first. It commits only after every artifact,
manifest, and dependency check passes. Failure restores the previous project
state and lock.

## Recovery And Pre-Release Replacement

The existing RWE-only shape uses `spec.libraries`. It is pre-release
scaffolding and is not the final v1 contract described here.

The implementation step must provide one explicit converter from that shape to
`spec.rwe.libraries`. Normal reads must not guess, silently rewrite, or accept
both structures indefinitely. After conversion, the canonical reader accepts
only the structure in this document.

A failed conversion preserves the original bytes and leaves a recovery copy for
inspection.

## Compatibility

Patch releases may improve error messages, scanning speed, hashing, locking, and
atomic I/O without changing accepted or emitted data.

Minor releases may add an optional field only when its absence has one fixed
meaning for all future releases. Existing field meaning, source values, path
rules, digest rules, ordering, and namespace ownership cannot change.

Renaming or moving a field, adding a source type, changing integrity meaning, or
changing which artifacts are locked requires a new contract API version and an
explicit converter. A `zebflow.com/v1` reader rejects newer versions.

### Before first release

Zebflow has not published a v1 release; no `zeb.lock` exists outside this
repository and its test instances, so `zebflow.com/v1` may be amended in place,
each amendment dated here. After first release this section closes and the
rules above apply literally.

| Date | Change | Why it was safe |
| --- | --- | --- |
| 2026-08-27 | Source vocabulary restructured: `embedded`/`hub`/`file` replaced by `hub.local`, `hub.public`, `hub.static`, `direct.npm`, `direct.file`, `project` | Pre-release, nothing shipped; old values refuse and the lock regenerates through ordinary resolution — no converter for documents that never existed. |
| 2026-08-27 | Node-bundle key fixed to the package coordinate (`publisher.package`, e.g. `zebflow.sim-des`), replacing the slash form the canonical example used | Pre-release, nothing shipped; no lock with a slash-form bundle key exists outside test instances. |
| 2026-08-27 | Node-bundle sources widened to `hub.*`, `direct.file`, or `project` | Pre-release, nothing shipped; the local-file node install already exists and had no lockable source value. |

## Frozen Implementation Guarantees

The v1 implementation provides:

1. One strict schema with separate `rwe` and `nodes` namespaces.
2. One `DependencyLockService` for all canonical reads, writes, migration,
   status, repair, and activation checks.
3. Saved-pipeline requirement scanning plus recursive composite-pipeline checks.
4. Exact resolution against installed RWE libraries, project node bundles, Hub
   provenance, and the native runtime registry.
5. Pipeline activation and runtime materialization gates without per-hit scans.
6. Project Studio status, refresh, and deterministic repair controls.
7. Deterministic fixtures, strict failure cases, tamper checks, and concurrent
   mutation tests.
8. Per-project Hub installation transactions that restore prior files and the
   prior dependency lock when registration or lock promotion fails.
9. Explicit pre-v1 conversion with a recovery copy. Normal reads accept only
   the canonical v1 structure.
10. A two-instance project transfer test that resolves both an RWE library and
    a real multi-file composite node bundle after import.
